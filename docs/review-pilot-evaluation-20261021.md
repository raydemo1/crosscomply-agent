## 实际观察

### 客户正式报告

首稿把“尚未提交已签合同、认证或备案证明”推成“已发生出境但未具备条件、存在既存合规缺口”。独立核心核验退回了这一推断。最终报告区分了：

- 已确认事实支持标准合同或认证机制，无需安全评估。
- 未提交证明不等于已经证明手续不存在，也不能据此确定违法。
- 报告完成不代表审批通过或可以立即执行。

最终为 `medium`，但保留手续完成、影响评估、告知等待核事项。将实际返回 payload 交给现有 `review_has_missing_information()` 和 `next_status_after_review()`，结果为 `needs_info`，不是直接提审。途中核心核验、建议栏目各超时一次，生产内置重试后成功。

### HR 免予待核

首稿把集体合同要件尚未确认的案件标为 `high`。核验器指出报告实质为条件分支，应保留不足状态，退回修订。

Agent 再次提交后，核心核验两次均在约 60.3 秒发生 `TimeoutError`，达到现有一次重试上限，任务以 `semantic_grounding / llm_api_error` 失败。没有最终报告，也没有评测 Judge 结果。

这是交付可用性失败；不能把它算成第二稿法律判断错误，也不能因为首稿被正确拦截，就声称该案已经成功完成审查。失败核验请求包含约 48,321 字符的用户消息、5 条 claim、11 条已引资料与 26 条背景资料。该事实只证明输入规模，尚不能证明超时由上下文体量单独导致；没有在本轮临时加超时、改流式或删资料后补抽。

### 冻结填报与材料冲突

最终账本保留 `confirmed_intake / not_ciio` 与 `material / ciio` 两条记录，均标为 `conflicted`，没有以确认填报压过相反材料，也没有用材料覆盖快照。

最终为 `insufficient_evidence`，`legal_path=null`，说明 CIIO 与非 CIIO 的不同分支，等待通知核验及填报更正。核验阶段曾退回风险边界的敏感人数表述和备案依据缺口，Agent 修订并补读后交付。该案耗时最长，不能仅因最终通过就忽略调查、修订和多栏目核验的累计成本。

### 申请人追问恢复

实际发生 `request_input → applicant_statement → resume`。脚本答复“我记得不是 CIIO、尚未核对通知”仍作为 `supplemental_statement / applicant_statement / unverified` 留在账本，没有升级为冻结确认事实。

最终为 `insufficient_evidence`、`legal_path=null`，保留条件分支；一次核心核验超时后，生产内置重试成功。

## 独立核验器当前如何工作

正常提交报告时，先执行程序门禁，再发起独立模型请求：

1. **程序门禁**：核对本轮已取得的引用、正式法条资格、材料版本归属、逐字原句，以及问题发现等结构化记录。
2. **核心核验**：独立请求接收完整候选报告、冻结填报、原始材料、来源账本、人工补充及实际已取得法源；检查 claims、摘要、正文、风险等级、法律路径、触发理由和缺口。它不继承调查思考，不自行检索。核心未通过就先退回。
3. **栏目核验**：核心通过后，分别对建议及问题发现、风险边界发起顺序请求，空栏目跳过。因此一稿通常最多 3 次核验请求，传输或输出协议失败可触发现有重试。
4. **聚合与修订**：程序聚合 `supported / unsupported / uncertain`，保留覆盖检查、原因、事实及法源缺口；未通过则把原稿与反馈交回原 Agent，由它决定修订或补查。定位只作辅助，不为缺少精确引句另加模型调用。

当前“独立”是职责、提示与请求上下文独立，**不是模型不同**：运行时把审查任务 `model_id` 传给核验器，本批两者实际都是 `deepseek-flash / low`。评测 Judge 则是额外的、仅用于评测的 `deepseek-flash / none` 请求，不参与产品审查和审批。

预算耗尽时存在受限的程序返回分支：只能生成 `insufficient_evidence`、没有 claims 且没有确定 `legal_path` 的系统不足报告；不能通过该分支交付有确定法律结论的报告。普通问答不走正式独立语义核验。

本批证明了几次实际退回与修订确实生效，也暴露出核验链路超时可造成整案不可交付。**同模型核验仍可能共享误判，核验通过不能等于法律正确，更不等于审批通过。**
