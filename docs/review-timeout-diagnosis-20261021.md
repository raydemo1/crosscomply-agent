# 正式核验超时：失败请求定向诊断

后续实现与验证见 [正式核验内部流式与超时修复](review-stream-timeout-fix-20261021.md)。下文保留当时诊断状态，不改写历史失败结果。

2026-10-21。诊断对象为正式审查首批中的 `review_hr_exemption_pending_001`，不重跑整案、不扩跑剩余 6 条、不修改生产提示、超时或核验门禁。

## 已确认的直接失败链路

1. Agent 提交第二稿后，进入独立核心核验 `semantic_grounding`。
2. `chat_json()` 使用 `response_format=json_object`、`thinking=enabled`、`reasoning_effort=low`，未启用 stream，未设置 max_tokens。
3. `_post_chat()` 使用 `urlopen(..., timeout=60)` 并一次 `response.read()` 取得完整响应后解析 JSON。该参数约束阻塞的 socket 操作，**不是独立的整案或模型推理总时限**。
4. 两次实际核验调用分别在 **60.313 秒、60.297 秒**发生 `TimeoutError: The read operation timed out`；没有完整响应和 usage。
5. `StructuredLLMNode` 的现有重试上限为一次。第二次仍失败后抛出 `ReviewWorkflowFailed(semantic_grounding, llm_api_error)`，整案未交付。

所以本案失败的直接位置是模型 HTTP 响应读取，不是 ES/PG 检索、法条引用门禁或一份已返回核验意见的语义退回。失败前第一稿曾被正确退回，那是另一条已完成调用。

## 两次固定请求重放

冻结原始 `model-call-007.request.json`，保持原消息、来源、报告、模型、low 和 JSON 输出模式。仅在诊断进程分别观察非流式和流式行为；不添加输出上限、删资料、改提示或择优重试。保留原有 HTTPS 代理路线。

| 指标 | 非流式诊断 | 流式诊断 |
|---|---:|---:|
| socket 超时，仅诊断 | 120 秒 | 60 秒 |
| HTTP 响应头 | 0.265 秒，200 | 0.219 秒，200 |
| 首响应体数据 | 60.265 秒 | 0.235 秒 |
| 首思考数据 | 非流式不能分时观测 | 0.641 秒 |
| 首正文 | 完整 JSON 在约 68.015 秒出现 | 50.453 秒 |
| 请求完成 | 68.078 秒 | 52.485 秒 |
| 思考 token | 13,546 | 10,163 |
| 总输出 token，含思考 | 14,355 | 10,562 |
| 最终 JSON 字符数 | 1,799 | 902 |
| 输入／缓存命中 token | 22,424／22,272 | 22,424／22,272 |
| 收到数据的最大观测间隔 | 起点到首数据约 60.265 秒；响应头到首字节恰为 60 秒 | 约 0.547 秒 |
| JSON Schema | 通过 | 通过 |

非流式 raw 响应在 JSON 前只有一个 `\n`。结合时序，响应头之后整整 60 秒才收到这次首个保活换行，之后约 7.75 秒取得 JSON。这与原来 60 秒读取超时发生在相同量级，构成了具体的保活间隔与客户端超时边界冲突证据。

[DeepSeek 官方保活说明](https://api-docs.deepseek.com/quick_start/rate_limit)确认，等待期间非流式可返回空行，流式可返回 SSE keep-alive 注释；文档没有承诺固定 60 秒保活频率。**这里的 60 秒是本次请求实测，不能外推为永久服务协议。**

## 为什么这份核验容易跨过 60 秒

- 第二稿核验的用户消息约 48,321 字符，其中已引和背景法源约 36,330 字符，报告约 6,689 字符；共 5 条 claim、11 条已引资料、26 条背景资料。
- 两次诊断的缓存命中率均约 99.3%，但思考分别达到约 1.35 万和 1.02 万 token，明显多于最终 JSON 本身。`low` 没有令本次生成天然限制在短时长内。
- 从 provider 思考记录的抽样检查，只能概括为反复核对相同的事实、豁免条件、条件性措辞与引用支持关系；客户端没有在这两次诊断中增加额外审查调用。思考用于定位耗时环节，不作为法律正确性证据，不在页面或报告中公开原文。
- 同案第一稿的核心核验输入 22,362 token、缓存未命中，思考 5,872 token，用时 34.656 秒。两稿输入规模相近而生成耗时不同，不支持把超时完全归因于输入过长或缓存未命中。

这些证据支持：**核验生成时间波动较大，非流式在长时间没有响应体数据时撞上客户端 60 秒读取边界，是本轮的明确可复现风险。**

不能进一步断言原失败请求恰好也生成了 13,546 token，或原请求一定在同一时刻返回保活：旧日志缺少分阶段和响应片段记录。服务端当时的排队、内部负载，以及旧请求是否存在临时链路问题，仍不能完全排除。当前重放连接快、缓存命中高，并不等于已还原旧请求的服务端内部时间线。

## 重试处理还存在的问题

第二次失败请求保留了原消息，但额外追加：

> 上一轮 LLM 调用或 JSON 解析失败。请只重新输出符合 schema 的 JSON/tool arguments，不要解释。 error=The read operation timed out

这把传输超时与 JSON／Schema 错误混在了一起。对没有拿到输出的请求追加格式纠错提示，不会增加读取等待时间，也没有针对超时原因；还会改变下一次模型输入。它不是本轮首个超时的原因，但应在重试设计中区分处理。

## 可以据此采用的修复方向

1. **核验内部用 SSE 接收，完整收齐后再执行原有 JSON、Schema、主张覆盖和语义状态检查。** 思考数据只用于保持接收与执行观测，不向用户展示；断流、长度截断和错误结果不能按通过交付。
2. **区分连接／首响应、读取空闲、总执行时限。** 超时预算应覆盖实际服务保活行为，总时限仍须有界，不能只把一个全局数值无界调大。
3. **传输失败与输出协议失败分别重试。** 超时按可重试传输错误处理，保留原输入；JSON/Schema/覆盖错误才使用相应纠错反馈。保留已有次数限制，不增加补证或报告循环。
4. **补足请求阶段观测。** 至少保留响应头、首事件／首思考、首正文、完成时间、最长无数据间隔及错误阶段，避免以后只能看到“60 秒失败”。

本轮仅完成诊断，没有实施这些生产变更。流式这一次更快的总耗时同时伴随更少生成 token，不能把 68.1→52.5 秒全部算成传输优化收益；本轮证明的是流式能在生成中持续收到数据。

两次重放的原始核验意见还分别为 `uncertain` 和 `supported`，这说明相同输入仍有判断波动。诊断只做 Schema 校验，没有继续执行全套栏目核验、原 Agent 修订或正式审批；**不以此次“收到 supported”把原 HR 失败用例改判通过，也不恢复全量评测**。
