# 问答引用标记简化、自动归一与受限修复

2026-10-21。在六次检索提示对照结束后，用户另行要求修复引用失败、简化标记，并核对strict与代码自动修复。生产主提示没有采用本次对照候选；本轮新增的是引用层程序修复。

## 实际失败原因

保存的HR问答最后一条原始回答中，两枚错误分别为：

- `[[cite:61368ea4d70fdb8af3104d5d]]`：它不是已发出的citation_marker，而是本轮已取得《促进和规范数据跨境流动规定》第六条chunk_id的完整尾部标识；正确引用标记为 `[[cite:4699f5e287a21ed8]]`。因此可按本轮精确来源身份自动映射，不需相似匹配。
- `[[cite:14f04395f6b4da]]`：正确已发出标记是 `[[cite:14f04395f6d4b4da]]`，模型在中间漏掉字符。不能仅因编辑距离最近就自动认定来源。

原程序在回答生成完毕后抛出ValueError；直接回答、带finish正文和最后流式回答均缺少受限的正文引用修复路径。程序没有放行无效引用，但可修复的小错误仍导致整个任务失败。

## 当前实现

1. 新发出的程序标记由16位十六进制缩短为8位。每轮登记表检查冲突，只延长新来源的标记，不改变已发出的标记；模型上下文、结果解析使用同一登记表。展示编号仍由程序生成。
2. 代码仅对确定的身份做归一：忽略十六进制ID的大小写和空白，修复缺少外层括号的完整已知标记，接受本轮完整chunk_id或唯一对应来源的完整chunk尾部标识。多个来源共享尾部时拒绝自动映射。不会按前缀、编辑距离、法名或条号猜匹配。
3. 仍不识别的完整标记汇总成一次错误。在同一回答Agent的原生历史上增加一次受限 `repair_citations` 调用，保留已取得原文、材料、对话和历史思考；不重新调查、不运行法律核验。旧标记与目标标记都用动态enum约束，目标只能来自本轮来源登记表。
4. 使用DeepSeek Beta原生tool calling的 `strict=true`，保持当前模型及思考设置、`tool_choice=auto`。strict仅用于引用补丁，不把普通Markdown正文误当成JSON Schema可控制的字段，也不为此修改所有调查工具Schema。
5. 模型只返回旧标记与新标记的对应关系。代码检查完整覆盖、无重复、来源归属及参数字段，再做字面替换；正文和其他有效标记不被模型重写。拒绝删除引用、选择外来来源或空补丁。只有校验通过才完成交付，失败不启动第二轮修复。正常回答与纯程序归一均不增加模型请求；修复占用原有轮次上限，预算不足仍拦截。

[DeepSeek官方文档](https://api-docs.deepseek.com/zh-cn/guides/tool_calls/)说明，strict约束Function参数，需走Beta且全部传入function开启strict，支持enum，数组minItems/maxItems等不受支持。补丁Schema只有一个工具，所有对象字段必填并禁止额外字段，数组完整覆盖由代码复查。没有增加SDK、兼容fallback或独立模型。

- 保存的失败回答原样回放，一次真实DeepSeek Beta strict调用成功，约2.25秒，45988输入token、282输出token，其中159为reasoning。两个替换均落在原登记表，原文内容保持不变；这只验证引用身份修复，不验证原回答的法律判断。
- 加入精确chunk身份映射后，再用同一失败回答做免费确定性回放：第一枚由代码解析，只有第二枚需要补丁。使用前述真实响应中的第二个补丁后全部标记通过，正文不变；没有为此重抽样或追加真实调用。
- 另以生产原提示完整跑一次 `eval_standard_contract_003`：39.735秒，3个模型请求，1次检索、2次精读、0次联网。使用8位标记直接完成，未触发修复请求，引用、材料归属、问答契约检查均通过。单样本不能证明引用错误率已降至零。

## 保留的问题

引用身份正确不保证来源支持段落的法律推导。此次完整QA仍把敏感个人信息或CIIO身份变化直接写成HR免予失效，未保持相应独立分支；“告知书只说明用途、需要补齐”也比用户实际给出的未知状态更强。这些是内容问题，未通过引用补丁改写或掩盖。当前受限修复也允许无法确定来源时拒绝补丁，因此不会保证所有未知标记都能自动恢复。
