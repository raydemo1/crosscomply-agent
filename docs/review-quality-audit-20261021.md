# 四条正式审查的逐字段质量复核

2026-10-21。复核首批四题的原始草稿、最终报告、核验请求与反馈；对照此前问答的问题。保留原始 pilot 评分与停止决定，不重算历史得分，不续跑另外六题。

随后按用户授权完成了[HR完整单题复测](review-hr-full-retest-20261021.md)：193.5秒交付，主结论、人数单位和分类本次未复现旧错，但仍遗漏单独同意的适用例外，生产核验与评测Judge均漏检。原四题记录及本页的定向试验结论保留，不能把新运行的自动评分通过等同于正文质量通过。

## 结论

正式审查确实出现了问答中同类的“缺事实／缺证明 → 确定法律后果”错误。客户题被核验并修正，HR 题的摘要及问题分类仍有问题。独立核验有实际拦截记录，但也会接受同类错误，不能用“核验通过”代替逐字段复核。

四题没有出现此前问答“日均处理量直接变成年度出境量”的同一事实口径推断，也没有复现推荐性标准被当作强制法律义务的直接证据。HR 摘要把已明确的人数写成“条”，是另一种单位表述错误。

## HR 的具体内容问题

第二稿来自 `review_hr_exemption_pending_001/model-call-007.request.json` 的 `report_background`，没有最终 payload：

> 现有记录不能证明已依法签订集体合同，跨境HR管理免予情形尚不成立；当年累计120万条非敏感个人信息出境已达申报门槛，未取得集体合同要件证据时应按数据出境安全评估办理。

1. “不能认定免予成立”可以是当前证据状态；“未取得证据时应按安全评估办理”进一步确定了机制后果。给定材料并未确认集体合同不存在，不能把这两者等同。正文末尾写不足、legal_path 留空，也不会使摘要中的这一推断自动正确。
2. 材料明确是累计去重 **120 万名员工**，摘要写成 **120 万条**。正文大部分仍写人数，属于报告内部单位不一致。
3. 第一条 issue.kind 为 `legal_gap`，第二条为 `missing_information`，实质围绕同一个集体合同未知。旧定义只说“材料事实与法条支持的法律问题”，模型将“免予主张未获证实”也理解成法律缺口。生产 `guided_actions_from_review()` 对 legal_gap 生成 control_remediation，因此这不是纯展示标签。
4. 正文引用了个保法第十三条处理基础，但本轮正式原文中没有该条，仅有解释资料及其他条款；这是引用／法律推导依据的边界问题，不能仅凭模型知道条号就当作已取得正式依据。这里不据此断言其法律内容必然错误。

原核心退回主要针对 high 风险标签；随后相同请求的流式／非流式诊断曾分别给出 supported 和 uncertain。因此“独立”不等于不同模型，也不保证纠正生成模型的推断。

## 其余报告的限制

- 客户题最终把缺证明与实际未履行分开。标准合同与认证择一已在正文明确；建议列表有直接签标准合同的措辞，存在分支表达不够明确的问题，但不能机械地把一种可选路径的操作建议当成虚构义务。接近门槛时准备评估也可能是审慎建议，不等同于法律门槛被改写。
- 冲突题风险边界用“非敏感超过100万人”，而主体规则和实际法源为“100万人以上”。该边界的充分条件仍落在规则内，但没有准确表达等于门槛的边缘；不能据此声称全部阈值表述已经统一。
- 申请人题的备案、影响评估等依据并非完全未取得：原栏目输入包含备案指南、标准合同办法、认证办法相关条文。它们大多未登记为最终交付来源。第一次核验接受整项手续建议，本轮重复核验对标准合同分支的单独同意依据提出 uncertain。应区分“没有检索到”“没有作为交付依据登记”和“核验判断不一致”。
- 三份最终报告的 conclusion 均无程序注入的行内引用标记，但结构化 claims 与引用卡片关系仍保留。当前只对唯一完整主张做定位；这些报告的 claims 是正文的改写，程序因此没有猜测挂载。未发现本批复现 QA 按正文顺序重编数字引用的直接证据；无行内标记也不等于引用已丢失。本轮没有恢复模糊挂载或为定位新增模型请求。

## 本轮修复

1. `report_groups()` 将每个 issue.kind 纳入现有建议／问题栏目核验和覆盖检查。仍是同一个栏目请求，没有增加核验阶段、模型或预算。
2. 明确现有 kind 契约：legal_gap 是材料与法条已共同支持的不合规行为、业务状态或方案缺口，供整改使用；决定缺口是否成立的事实未知用 missing_information，条件后果写在 finding 或正文。生成工具 Schema 与栏目核验共用 `ReviewIssueDraft.kind` 描述，避免各自定义。
3. 分类退回沿用原稿与 revision_targets 返回 Agent，由 Agent 修订；不自动把 legal_gap 改成 missing_information，不以 unknowns 非空判错，不改变引用或审批门禁。

没有改写历史回答、回填已失败任务结果，或增加针对 HR、CIIO、人数的硬编码规则。摘要未知转确定、单位错误和未声明使用来源，仍属于需要继续验证的生成／核验质量问题。

## 定向验证与证据边界

第一阶段 `data/review_runs/review_quality_audit_20261021/`：原 HR 第二稿、原始事实及全部已取得法源，比较旧栏目协议与增加 kind 的协议；另检查原申请人报告。三次逻辑调用均成功且未重试：

- 旧 HR 栏目：所有单元 supported。
- 增加 kind 后的 HR 栏目：仍全部 supported，模型仍把“未证实”解释为法律缺口。**仅补覆盖未产生本例判断收益。**
- 申请人题：missing_information 分类仍通过，但另一项手续依据 uncertain。不能据该结果宣称分类改动提高了整体质量。

该阶段还记录一次脚本本地序列化预检失败，在任何模型调用前修复；与法律质量评分分开。

第二阶段 `data/review_runs/review_issue_contract_20261021/`：明确分类契约后，固定原 HR、申请人报告，再加一条独立虚构许可规则的正向控制，检查确有方案缺口但整改日期未知时能否保留 legal_gap。完整结果与使用量保存在该目录，不运行完整 Agent 或 Judge。

两阶段合计六次逻辑调用，各一次实际请求、无重试；每阶段源码运行前后指纹一致。第二阶段提供分类检查生效的一条轨迹证据，不能把第一阶段的未改善结果隐藏，也不能把申请人题前后一次不同核验意见归因于分类定义。

新增及更新程序回归覆盖 kind 进入核验目标、分类退回覆盖已支持正文、返回可修订字段且不自动改稿，以及已成立问题可带其他未知。最终后端全量 **920 passed**；Ruff 与 `git diff --check` 通过。本轮只修改报告契约、栏目核验及相关测试和复核记录，没有前端变更。

本轮定向调用不修改报告，没有重跑完整四题或 HR 完整执行链，不能给出修复后的正式审查通过率。样本只用于检查分类契约，不能证明已经消除正文错误。
